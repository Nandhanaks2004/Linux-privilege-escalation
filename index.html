Introduction

What is Linux Privilege Escalation?

Privilege escalation is the technique by which an attacker moves from a limited user account to a higher-privileged account — ultimately root — through system misconfigurations, weak permissions, and vulnerable software.

On Linux systems, an attacker typically gains initial access through a basic user or service account (like www-data) with limited privileges. The goal of privilege escalation is to reach the root user — the default super-user account with unrestricted system access.

Attackers are never satisfied with limited access. They need root to install backdoors, steal sensitive data, deploy ransomware, or pivot deeper into the network. Understanding how they do this is essential for every security professional.

A normal user account is like access to a building lobby. Privilege escalation is finding a way into the master control room — where every camera, lock, and security system can be controlled.

Fundamentals

Linux Access Control Fundamentals

Understanding how Linux manages users, groups, and permissions is essential before exploring escalation techniques.

01

Linux Multi-User Architecture

▼

Linux was designed as a multi-user operating system from the ground up. Unlike early Windows systems, Linux separates users and privileges at the kernel level. This architecture is both a strength and a weakness — misconfigured permissions create escalation paths that attackers exploit.

Key Concept: UID

Every user on a Linux system is identified by a User ID (UID). The root user always has UID 0. If any other user is assigned UID 0, they implicitly have root privileges — a dangerous misconfiguration attackers actively look for.

/etc/passwd — User Database Format
username:x:UID:GID:Info:Home:Shell
root:x:0:0:root:/root:/bin/bash
jane:x:1002:1002:Jane D.:/home/jane:/bin/bash
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin

Red flag: Users with UID 0 or users added after system installation (UID > 1000) running services are common escalation targets.

03

Special Permissions: SUID, SGID, Sticky Bit

▼

Special permissions change how executables and directories behave. For privilege escalation, SUID is the most critical — it allows a binary to run with the file owner's privileges, regardless of who executes it.

Bitchmod ValueSymbolEffect
SUID4xxx (e.g. 4755)s in owner executeRuns as file owner (often root)
SGID2xxx (e.g. 2755)s in group executeRuns with group privileges
Sticky1xxx (e.g. 1755)t in others executeOnly owner can delete (e.g. /tmp)
SUID Detection — Attackers Run This First
$find / -perm -4000 -type f 2>/dev/null
Result/usr/bin/find (root — SUID)
Result/usr/bin/python3 (root — SUID)
Result/usr/bin/pkexec (root — SUID)

If find has the SUID bit set and is owned by root, any user can run find with root privileges — enabling command execution as root.

Attack Types

Horizontal vs Vertical Privilege Escalation

Attackers use two distinct strategies to gain higher privileges. Understanding the difference is key to defending against both.

Horizontal Privilege Escalation

www-data → jane → bob

The attacker compromises another user account with similar or higher privileges than the initial account. This is more common because moving between users is often less monitored than escalating to root. Attackers search for SSH keys, reused passwords, and readable home directories.

Vertical Privilege Escalation

www-data → root

Sometimes called "privilege elevation," the attacker uses a single compromised account to gain root access directly — through SUID binaries, misconfigured sudo, kernel exploits, or writable root-owned scripts. This is the ultimate goal of most Linux attacks.

▼

Cron jobs are scheduled tasks that run automatically. If a root-owned cron job executes a script that is writable by a lower-privileged user, that user can inject malicious commands that run as root.

13

PATH Hijacking

▼

PATH hijacking exploits the order in which Linux searches for executables. If a root-owned script calls a command without a full path (e.g., backup instead of /usr/bin/backup), an attacker can place a malicious binary earlier in the PATH.

Root Script calls:
system("backup")
→
/tmp/backup (attacker-created)
PATH=/tmp:$PATH
→
Root execution
Malicious binary runs as root
PATH Hijacking Technique
$echo $PATH
/usr/local/bin:/usr/bin:/bin:/usr/local/games
$echo '#!/bin/bash' > /tmp/backup
$echo 'cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash' >> /tmp/backup
$chmod +x /tmp/backup
$export PATH=/tmp:$PATH
$# Wait for root cron job — /tmp/rootbash appears (SUID)

16

Kernel Exploitation Concepts

▼

Kernel exploits target vulnerabilities in the Linux kernel itself. They are powerful but risky — often causing system crashes or instability. Attackers use them as a last resort when other escalation paths fail.

Dirty COW (CVE-2016-5195)

Race condition in copy-on-write mechanism. Allowed unprivileged users to write to read-only memory mappings — including overwriting /etc/passwd to create a root user.

Race Condition

Full Nelson / Half Nelson

Local privilege escalation exploits affecting older Linux kernels. Leveraged weaknesses in the kernel's handling of certain system calls.

Syscall Exploit

Dirty Pipe (CVE-2022-0847)

Vulnerability in Linux kernel pipe mechanism. Similar impact to Dirty COW — allowed overwriting arbitrary read-only files including binaries and passwd.

Pipe Exploit

PwnKit (CVE-2021-4034)

Vulnerability in pkexec — SUID binary present on all major Linux distributions. Simple exploitation led to immediate root access.

SUID Exploit
Kernel Exploit — Workflow (Conceptual)
1.Identify kernel version with uname -a
2.Search exploit databases for matching CVEs
3.Compile or cross-compile exploit for target architecture
4.Transfer exploit to target (wget, curl, base64)
5.Execute — potential system instability warning

▼

Defense

Linux Hardening & Defense

Understanding how attackers escalate privileges is the first step. The second is implementing defenses that make their job exponentially harder.

BEFORE — Vulnerable Configuration

  • World-writable scripts running as root
  • All users can sudo with no password
  • SUID binaries uncontrolled and unmonitored
  • /etc/shadow readable by all users
  • No session logging or auditing
  • Unpatched kernel and services

AFTER — Hardened Configuration

  • Strict file permissions — no world-writable root scripts
  • Limited sudo access with password + MFA
  • SUID binaries audited and minimized
  • /etc/shadow readable only by root
  • Auditd + SIEM monitoring for privilege abuse
  • Regular patching with vulnerability management
